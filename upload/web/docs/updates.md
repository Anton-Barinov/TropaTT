# Обновления TropaTT

TropaTT умеет обновляться прямо со страницы администрирования — без SSH, Composer
и ручной замены файлов. Система состоит из двух частей:

1. **Сервер обновлений** (`update.tropatt.com`) — заранее собирает готовые
   архивы обновлений из GitHub и подписывает их.
2. **Updater в самой CRM** (`updater/`) — скачивает готовый архив, проверяет
   подпись, делает backup, применяет файлы и миграции БД, умеет откатываться.

Пользовательский интерфейс — страница **Администрирование → Обновления системы**
(`web/index.php?route=admin-updates`).

---

## Как это работает: общая картина

```
GitHub (Anton-Barinov/TropaTT, ветка main)
        │  каждые 10 минут
        ▼
Сервер обновлений update.tropatt.com
        │  cron.php run: scan-github → process-builds → publish-channels → cleanup
        │  full- и delta-архивы + подписанный manifest
        ▼
Ваша CRM (updater/)
        │  страница «Обновления системы»
        ▼
Проверка → безопасность (preflight) → архив → установка → backup → откат при ошибке
```

## Часть 1. Сервер обновлений: сборка пакетов

Сервер обновлений — отдельное PHP-приложение, развёрнутое на
`update.tropatt.com`. Оно не хранит «сборок» вручную: оно зеркалирует репозиторий
GitHub и по cron пересобирает пакеты при появлении новых коммитов.

### Крон-скрипт

Каждые 10 минут выполняется:

```cron
*/10 * * * * /usr/bin/php /home/tropatt/web/update.tropatt.com/public_html/bin/cron.php run >> .../storage/logs/update-center-cron.log 2>&1
```

`bin/cron.php run` последовательно запускает четыре команды:

| Команда | Что делает |
|---|---|
| `scan-github` | Обновляет git-mirror (`storage/repos/TropaTT.git`) и находит новые коммиты в ветке `main`, которых ещё нет в базе. |
| `process-builds` | Для каждой новой сборки: планирует изменения, собирает full- и delta-архивы, подписывает пакет и manifest. |
| `publish-channels` | Публикует собранные сборки в каналы `nightly` и `stable` по политикам канала. |
| `cleanup` | Чистит истёкшие lock-файлы. |

Отдельные команды можно запускать вручную:

```bash
php bin/cron.php scan-github
php bin/cron.php process-builds
php bin/cron.php publish-channels
php bin/cron.php build-status     # показать все сборки JSON
php bin/cron.php reset-locks      # сбросить истёкшие блокировки
php bin/cron.php rebuild --sha=<sha>   # пересобрать конкретную сборку
php bin/cron.php bootstrap-build --sha=<sha> [--from=<sha>]  # первая сборка от базового коммита
```

### Что хранится

- `storage/repos/TropaTT.git` — зеркало GitHub-репозитория
- `storage/worktrees` — рабочие копии для сборки конкретного коммита
- `storage/packages` + `packages/` — собранные архивы
- `storage/manifests` — подписанные манифесты
- `storage/logs` — логи крон-скрипта
- БД (MySQL) — таблицы commits, builds, packages, channels

### Конфигурация продукта

`app/Config/products.php` описывает продукт `tropatt-core`:

- `repository_url` — GitHub-репозиторий
- `branch` — ветка (`main`)
- `base_version` — базовый номер версии
- `version_file` — файл с версией внутри репозитория (`upload/VERSION`)
- `channels` — каналы `nightly`, `stable`, `hotfix`
- `core_paths` — какие пути попадают в пакет обновления
- `excluded_paths` / `forbidden_paths` — что никогда не попадает (`.env`,
  `modules/**`, `storage/**` и т.д.)

### Каналы и политики публикации

| Канал | Политика сборки | Макс. риск для авто-публикации | Авто-публикация |
|---|---|---|---|
| `nightly` | `each_commit` — сборка на каждый коммит | `high` | да |
| `stable` | `head_batch` — сборка на текущую голову ветки | `medium` | да |
| `hotfix` | `manual` — только вручную | `high` | нет |

CRM по умолчанию работает с каналом **`stable`** (настраивается переменной
`TROPATT_UPDATE_CHANNEL` в `api/.env`).

### Как формируется пакет

1. `BuildFactory` создаёт запись сборки (`queued`) и оценивает риск по списку
   изменённых файлов (`BuildRiskAnalyzer`).
2. `BuildProcessor` для каждой `queued`-сборки:
   - проверяет/создаёт пары ключей подписи RSA;
   - делает worktree нужного коммита;
   - собирает **full-архив** (`tropatt-core-<build>.zip`, полный набор файлов)
     и **delta-архив** (`tropatt-core-<from>--<build>.zip`, только изменённые
     файлы между сборками);
   - вычисляет SHA-256 каждого файла и всего архива;
   - подписывает SHA-256 архива и содержимое manifest секретным ключом;
   - сохраняет manifest (add/modify/delete/rename + подпись).
3. `BuildPublisher` публикует сборку в канал в соответствии с политикой канала.

Важно: **манифест и пакет подписаны** закрытым ключом сервера обновлений.
Клиентская CRM проверяет подпись публичным ключом
(`updater/keys/update_public.pem`) перед любыми изменениями файлов.

### API сервера обновлений

`/api/v1/...`:

- `products/{product}` — информация о продукте
- `products/{product}/channels/{channel}` — канал и его сборки
- `products/{product}/update-plan?current_build=...` — план обновления
  (есть ли новая сборка, какой пакет рекомендован)
- `products/{product}/changes` — список изменений между версиями
- `manifests/{product}/{from}/{to}` — delta-manifest
- `manifests/{product}/full/{to}` — full-manifest
- `products/{product}/public-key` — публичный ключ для проверки подписи

## Часть 2. Поток обновления для пользователя

### Где находится страница

**Администрирование → Обновления системы**
(`web/index.php?route=admin-updates`).

Доступ: только root/администратор с правом управления настройками (иначе 403).

### Шаг 1 — «Проверить обновления»

CRM запрашивает у сервера обновлений план: `current_build` → `target_build`,
рекомендованный пакет, уровень риска, список изменений. На странице появляются
KPI:

- **Текущая версия** — установленная сборка (например `20260731.002`)
- **Доступная версия** — целевая сборка (например `20260731.005`) или `latest`
- **Что скачается** — тип пакета (FULL / DELTA) и размер
- **Уровень риска** — низкий / средний / высокий / критичный

### Шаг 2 — «Проверить безопасность» (preflight)

Безопасная проверка: **файлы CRM не меняются**. Проверяется:

- доступность сервера обновлений;
- подпись manifest и подпись пакета (криптографически);
- доступность URL пакета и соответствие размера;
- наличие расширений PHP `zip` и `openssl`;
- права на запись каталогов `api/`, `web/`, `storage`;
- отсутствие запрещённых путей в пакете (zip-slip, `.env` и т.д.);
- достаточное свободное место на диске;
- отсутствие активной блокировки обновления.

Только после **всех** успешных проверок (14/14) можно идти дальше.

### Шаг 3 — «Подготовить архив» (download)

CRM скачивает рекомендованный пакет во временную папку
(`storage_api/updates/packages/`) и распаковывает в staging
(`storage_api/updates/staging/`). **Рабочие файлы CRM снова не трогаются** —
это только подготовка.

### Шаг 4 — «Установить обновление» (apply)

Перед установкой CRM запрашивает подтверждение (введите `APPLY`). Процесс:

1. Включается **maintenance mode** — сайт временно недоступен для пользователей.
2. Создаётся **backup** всех файлов, которые будут изменены или удалены
   (`storage_api/updates/backups/`).
3. Применяются файлы из пакета (add / modify / delete).
4. Проверка здоровья системы (health check).
5. Применяются **миграции БД** (если в пакете есть новые миграции).
6. Обновляется локальный `installed-core.json` — новая сборка становится
   «текущей».
7. Maintenance выключается. CRM снова работает.

Результат установки показывается на странице: job ID, количество обновлённых
файлов, ID backup, статус миграций, установленная сборка.

### Шаг 5 — «Восстановить из backup» (rollback)

Если после установки что-то пошло не так (ошибки, нестабильная работа),
доступна кнопка **«Восстановить из backup»** (подтверждение: введите
`ROLLBACK`). Процесс:

1. Включается maintenance mode.
2. Файлы восстанавливаются из последнего backup.
3. Проверка здоровья.
4. `installed-core.json` возвращается на предыдущую сборку.
5. Maintenance выключается.

Rollback работает только если есть backup (`can_rollback: true`). После
отката обновление можно попробовать снова.

### Безопасность процесса

- Пакет и manifest **подписаны** — CRM проверяет подпись перед применением.
- **Защищённые пути** (`modules/**`, `storage/**`, `storage_api/**`, `uploads/**`,
  `backups/**`, `logs/**`, `cache/**`, `.env`, `api/config/*.local.php`, ...)
  никогда не изменяются пакетом.
- Операции **apply / rollback** требуют одноразового updater-token, который CRM
  получает отдельным запросом (эндпоинт `session` API CRM).
- Действия **preflight / download** ограничены **rate limit'ом** по IP клиента
  (по умолчанию 20 запросов за 5 минут, далее блокировка 15 минут с ответом
  429 + заголовок `Retry-After`). Обычный поток обновления делает 2–3 запроса,
  поэтому лимит никогда не мешает.
- Настройки лимитов — в `api/config/update.php` (`rate_limits`).

### Требования к хостингу

Система обновлений рассчитана на **самый простой виртуальный хостинг**:

- только PHP (8.1+) + MySQL, никаких shell-утилит для пользователя;
- всё обновление управляется из браузера;
- backup и staging хранятся внутри каталога `storage_api/` (должен быть
  доступен на запись);
- таймаут запроса увеличен до 600 секунд для длительных операций
  (backup + применение файлов + миграции);
- никаких Composer/npm/SSH — обновление работает через браузер.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| «Сервер обновлений недоступен» | Сервер `update.tropatt.com` не отвечает или `TROPATT_UPDATE_CENTER_URL` настроен неверно. Проверьте сеть хостинга (должен быть доступен HTTPS-запрос). |
| «Не удалось проверить подпись» | Публичный ключ `updater/keys/update_public.pem` не совпадает с ключом сервера обновлений. |
| 429 RATE_LIMITED | Слишком частые запросы preflight/download с одного IP. Подождите время из `Retry-After` (обычно до 15 минут). |
| Установка прервана mid-way | Снова нажмите «Установить обновление» — job и подготовленный staging сохраняются, установка продолжится с сохранённого состояния. |
| После установки ошибки | Нажмите «Восстановить из backup» и сообщите job ID. |
| Миграции БД не применены | Иногда миграции требуют ручного повторного запуска. В отчёте установки видна секция «Миграции БД» (применены / не применены + причина). |

## Разработка и деплой обновлений (для сопровождающих)

1. Внесите изменения в репозиторий GitHub и **поднимите версию** в
   `upload/VERSION` (например `1.0.1`).
2. Сервер обновлений сам подхватит новые коммиты по cron (в течение ~10 минут)
   и соберёт/подпишет пакеты.
3. Проверьте статус на сервере обновлений: `php bin/cron.php build-status`.
4. При необходимости пересоберите сборку: `php bin/cron.php rebuild --sha=<sha>`.
5. Готовые пакеты появятся в канале `stable` автоматически, если риск сборки
   ≤ `medium`.

> **Внимание.** Рейт-лимитер апдейтера (новые файлы
> `updater/src/Security/RequestRateLimiter.php`, `RequestRateLimiter` в
> `UpdaterKernel.php`, конфиг `rate_limits` в `api/config/update.php`)
> является частью кода CRM и доставляется обычными обновлениями. Если вы
> вносите правки в `updater/` локально, обязательно коммитьте их в GitHub,
> чтобы пакеты сервера обновлений включали актуальный апдейтер.

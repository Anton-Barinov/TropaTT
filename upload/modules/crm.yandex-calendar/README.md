# crm.yandex-calendar

Приватная двусторонняя интеграция Яндекс.Календаря с TropaTT CRM через CalDAV.

## Важное ограничение API

У Яндекс.Календаря нет публичного REST/JSON API событий с обычным OAuth authorization-code flow для личных аккаунтов. Поэтому модуль **не имитирует OAuth** и не принимает обычный пароль Яндекс ID. Для личного календаря используется официальный CalDAV-доступ и отдельный пароль приложения «Календарь».

Для организаций Яндекс 360 доступ к ресурсам пользователей может строиться через сервисное приложение и краткоживущий токен обмена. Это отдельный административный сценарий, он не равнозначен личному OAuth и в текущей версии намеренно не включён: нельзя безопасно выдать CRM права на календарь сотрудника без явной политики администратора домена.

Официальные источники:

- [Синхронизация Яндекс.Календаря с приложениями](https://yandex.ru/support/yandex-360/business/calendar/ru/data-exchange/synchronization/sync-desktop)
- [Сервисные приложения Яндекс 360](https://yandex.ru/support/yandex-360/business/admin/en/security-service-applications)
- [OAuth Яндекс ID](https://yandex.com/dev/id/doc/en/)

## Настройка пользователя

1. В настройках безопасности Яндекс ID создайте отдельный пароль приложения для календаря.
2. На странице модуля укажите email Яндекса и этот пароль приложения.
3. Модуль проверит доступ к CalDAV **до** сохранения секрета.
4. `APP_SECRET` должен быть задан в конфигурации CRM: пароль хранится только в зашифрованном виде.

Секреты не возвращаются API, не пишутся в логи и не попадают в HTML/JS.

## Синхронизация

- CalDAV discovery находит доступные календари пользователя.
- События запрашиваются REPORT `calendar-query` в окне `YANDEX_SYNC_DAYS_PAST` / `YANDEX_SYNC_DAYS_FUTURE` (по умолчанию 90/365 дней). Один запуск ограничен `YANDEX_MAX_EVENTS_PER_SYNC` (по умолчанию 5000), чтобы shared-hosting не исчерпал память и время выполнения.
- Пагинация не требуется для REPORT; количество событий рекомендуется ограничивать политикой установки и размером окна.
- Push/webhook для CalDAV Яндекс.Календарь публично не предоставляет, поэтому используется cron каждые 15 минут.
- UID и `RECURRENCE-ID` используются как ключи mapping. Повторяющиеся ресурсы импортируются в CRM только master-событием: `RRULE` сохраняется, а отдельные исключения не раскладываются в независимые CRUD-записи, чтобы изменение одной записи не уничтожило весь ICS-ресурс.
- Если удалённое событие исчезает из ограниченного окна, локальная запись удаляется только когда её сохранённая дата попадает в тот же диапазон.
- В двустороннем режиме первый включённый writable-календарь используется для новых CRM-событий, чтобы не создавать дубликаты в нескольких календарях.
- При конфликте HTTP `412 Precondition Failed` запись не перезаписывается молча: синхронизация сообщает предупреждение.
- CalDAV href разрешаются только на `https://caldav.yandex.ru`; XML разбирается с `LIBXML_NONET`, а создание локального события и mapping выполняется одной транзакцией.

## Приватность

Связь принадлежит `user_id` текущего пользователя. Все API-методы получают connection/source только с проверкой владельца. Синхронизированные события помечаются `source_type=yandex_calendar` и `source_owner_user_id`; корневой пользователь не получает их автоматически через общий календарь. При отключении удаляются mapping, секрет и принадлежащие владельцу приватные события.

## Ограничения текущей версии

- Участники, ACL, напоминания, цвета и вложения не переносятся: CalDAV-данные не имеют безопасного прямого аналога в текущей модели CRM.
- Инкрементальные RFC 6578 sync-token не используются из-за неоднородной поддержки на CalDAV-серверах Яндекса; сверка выполняется bounded full query.
- Фоновая синхронизация требует настроенного cron TropaTT. На shared-hosting это безопасный fallback без публичного webhook.
- OAuth для личного Яндекс.Календаря не заявляется как поддержанный, потому что такой публичный event API и scope в официальной документации отсутствуют.
- SQL-миграция рассчитана на MySQL/MariaDB, как и остальные production-модули CRM; локальные unit-тесты используют SQLite только для репозиторных сценариев и не заменяют проверку миграции на MySQL.

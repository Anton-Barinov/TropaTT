# crm.automation-hub

Модуль подключает n8n и Make как получателей событий TropaTT CRM. Он создаёт штатную подписку `webhook_subscriptions`, поэтому реальные события CRM попадают в общую очередь `webhook_deliveries` и отправляются системным обработчиком webhooks. Модуль не реализует входящие сценарии, произвольные команды в CRM или автоматическую синхронизацию данных из n8n/Make обратно в CRM.

## Что работает

- Создание подписки на endpoint n8n или Make с выбором событий: `task.created`, `task.updated`, `task.status_changed`, `project.created`, `project.updated`, `comment.added`, `intake.created`.
- Доставка событий через общую очередь CRM с подписью, повторами, статусами и dead-letter поведением ядра. Историю и ошибки доставки смотрите в Администрирование → Webhooks.
- Остановка и возобновление синхронно меняют состояние подключения Automation Hub и связанной подписки ядра.
- Ручной тестовый ping отправляется напрямую из модуля. Для повтора с неизвестным исходом браузер сохраняет correlation ID на время вкладки; повторный запрос использует тот же ID и не создаёт вторую отправку.
- Рецепты и подписки изолированы по активному рабочему пространству. Секреты не возвращаются в список и не пишутся в логи.
- Существующие рецепты без подписки после обновления восстанавливаются при нажатии «Восстановить подписку». Для такой старой записи по умолчанию выбирается `task.created`; повторно вводить уже зашифрованный секрет не требуется.
- При откате миграции связь с рецептом удаляется, но системные webhook-подписки и история доставок сохраняются. Их можно отключить или удалить в штатном разделе Webhooks.

## Права и границы

Для просмотра списка нужно `settings.view`. Для создания, восстановления, паузы, возобновления и тестового ping нужно `webhook.manage`. Пункт меню показывает модуль пользователям с этим правом.

Выбранные события отправляются только наружу. Содержимое проходит штатную фильтрацию ядра: секреты, токены, пароли и финансовые поля исключаются. Не включайте секреты или персональные данные в заголовки/описания задач; получатель endpoint контролируется администратором рабочего пространства.

Модуль пока не содержит визуальный конструктор сценариев, маппинг полей, двусторонние действия, встроенный каталог шаблонов n8n/Make или собственную таблицу журнала. Не позиционируйте эти возможности как доступные.

## Требования

- PHP 8.1+, PDO/MySQL, cURL на хостинге для фактической сетевой доставки и OpenSSL.
- `APP_KEY` длиной не менее 32 символов.
- Endpoint должен быть публичным HTTPS на порту 443. Запрещены localhost, private/link-local/reserved IP, URL с userinfo, query или fragment. DNS-проверка выполняется при сохранении и повторно перед отправкой.
- В CRM должен работать системный обработчик очереди webhooks (cron/планировщик TropaTT). Создание очереди не означает, что удалённый получатель уже принял запрос.

## Проверка в браузере и API

1. В тестовом workspace создайте подключение к контролируемому HTTPS endpoint. Выберите `task.created`; сохраните его и убедитесь, что секрет не отображается повторно.
2. Создайте задачу обычным способом в том же workspace (через UI или REST API). В разделе Webhooks должна появиться queued доставка именно для этой подписки.
3. Дождитесь системного обработчика и проверьте конечный статус/ответ. Убедитесь, что в payload есть `task.created` и task public ID, но нет секрета, пароля или финансовых полей.
4. Повторите создание события в другом workspace: доставка первой подписки не должна появиться.
5. Отключите подключение и создайте ещё одну задачу: новая доставка не должна ставиться в очередь. Возобновите и повторите.
6. Нажмите тестовый ping, имитируйте потерю ответа, затем повторите проверку с той же вкладки. Должен использоваться тот же correlation ID; получатель не должен видеть дубль.
7. Проверить endpoint с `http`, localhost, private/link-local/reserved IP, DNS-ответом с частным адресом, слишком большим ответом и timeout — такие цели должны отклоняться/завершаться безопасным состоянием.
8. Проверить страницу и формы на desktop и мобильной ширине: переполнение, фокус клавиатуры, сообщение пустого списка, ошибки API, выбранные события и состояние восстановления старых подписок.

## Локальные проверки

Запустить `RecipeStateTest.php`, `EventOutboxIntegrationTest.php`, `ReleaseHardeningTest.php`, `php -l` для изменённых PHP-файлов и `node --check web/assets/js/automation-hub.js`. Перед выпуском прогнать полный быстрый набор CRM и вручную проверить созданное событие на тестовом сайте; не использовать production-получателей.

## Требования

- PHP 8.1+, PDO/MySQL и PHP cURL с поддержкой `CURLOPT_RESOLVE`.
- Настроенный `APP_KEY` длиной не менее 32 символов и OpenSSL.
- Внешний endpoint должен быть публичным HTTPS на порту 443; private/loopback/link-local/reserved адреса блокируются. URL с userinfo, query или fragment не принимаются.

## Ручная проверка

1. Для просмотра подключений нужны `settings.view` и активное рабочее пространство; для создания подключения, паузы/возобновления и тестового ping нужно `webhook.manage`. Список должен содержать только подключения текущего пространства.
2. Создать тестовое подключение с синтетическим секретом и контролируемым HTTPS endpoint. Убедиться, что секрет очищается из формы после сохранения и не появляется в ответах/DOM/логах.
3. Нажать «Отправить тестовый ping» только для контролируемого endpoint; проверить HMAC заголовки, HTTP результат и отсутствие записи payload в CRM-журнале.
4. Проверить отклонение `http://`, localhost, приватных и link-local IPv4/IPv6, metadata адресов, URL с userinfo/query, DNS ответов, содержащих непубличный IP, и DNS rebinding между сохранением и доставкой.
5. Проверить отказ для неверного workspace, недоступного `APP_KEY`, некорректного/старого формата секрета, слишком большого payload/ответа и timeout.
6. Проверить desktop и mobile ширины, ошибки API, пустой список и повтор загрузки. Никакие реальные пользовательские данные не использовать.

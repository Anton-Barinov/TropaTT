# ТЗ для агента: языковой модуль TropaTT CRM

Версия документа: 1.0  
Назначение: создание, проверка, упаковка, публикация и сопровождение нового
языка интерфейса TropaTT CRM.  
Эталон: установленный пакет `crm.language-pack-ar-sa` (арабский, RTL).

Документ является практическим заданием для агента. Он описывает результат,
который должен быть получен, а не только замену слов в одном файле. Новый язык
считается готовым только после проверки серверного HTML, динамического JavaScript,
API, всех внутренних маршрутов, мобильного интерфейса, кэша и установки через
маркетплейс.

## 1. Цель и границы работ

Агент должен добавить локаль `<locale>` так, чтобы:

* выбранный язык применялся одинаково на логине, в шапке, боковом меню, всех
  внутренних страницах, модальных окнах, уведомлениях, пустых состояниях,
  ошибках API и динамических виджетах;
* одна локаль не подтягивала случайные русские, английские или другие строки из
  неправильного fallback-слоя;
* для RTL-языка интерфейс был зеркально перестроен, а для LTR сохранил обычное
  направление;
* новый пакет можно было установить ZIP-файлом и через
  **Администрирование → Модули → Маркетплейс**;
* обновление пакета не ломало установленную CRM, пользовательские данные,
  рабочие пространства, права, настройки и другие модули;
* пакет имел воспроизводимую версию, контрольную сумму и понятное описание для
  каталога маркетплейса.

Работа включает web-слой и API-слой. Переводятся только пользовательские тексты.
Идентификаторы, URL, имена PHP-классов, публичные ключи, коды ошибок, названия
таблиц и значения JSON-контрактов переводить нельзя.

## 2. Обязательный порядок изучения перед изменениями

Перед началом агент читает:

1. `AGENT_CONTEXT.md`, `AGENTS.md`, `AGENT_PIPELINE.md` и применимые регламенты
   в Базе Знаний CRM.
2. `docs_modules/modules_ru.md` и `docs_modules/modules_en.md` — правила модулей,
   упаковки и установки.
3. `upload/web/system/I18n/I18n.php` — сборка каталога web-переводов.
4. `upload/web/system/I18n/EarlyResponse.php` — локаль до создания обычного
   ответа (логин, ошибки, ранние endpoint'ы).
5. `upload/web/assets/js/i18n.js` — применение `data-i18n`, placeholder, title,
   aria-label и динамических строк.
6. `upload/api/system/library/service/LanguagePackInstaller.php` — точная схема
   ZIP, AST-проверка, установка, экспорт, контроль SHA-256.
7. `upload/api/system/library/language/LanguageRegistryService.php` и
   `upload/api/system/library/language/LanguageManager.php` — реестр, направление,
   включение, fallback API.
8. Эталонные файлы установленного Marketplace-пакета и
   `upload/web/language/supplemental/packs/<locale>.php` для поздних
   исправлений; в core-репозитории встроены только `ru-ru`, `en-gb` и `zh-cn`.
9. `tests/run_local.sh`, `tests/run_all.sh`,
   `upload/api/scripts/audit_web_i18n.php` и
   `upload/api/scripts/audit_api_i18n.php`.

Если локальная База Знаний или регламент противоречит этому документу, агент
фиксирует расхождение и следует более свежему регламенту владельца проекта.
Секреты, токены, cookie, `.env`, SSH-ключи и внутренние URL с доступами в пакет
и документацию не включаются.

## 3. Модель локализации, которую нельзя нарушать

### 3.1. Коды и метаданные

Используй нормализованный код BCP-47 в нижнем регистре, например `he-il`,
`tr-tr`, `ja-jp`. Код должен соответствовать регулярному выражению установщика:
`^[a-z]{2,3}(-[a-z0-9]{2,4})?$`.

Добавь локаль в каждый слой, где перечислены локали:

* реестр/список доступных языков;
* ранняя нормализация запроса и cookie;
* web-каталог;
* API-каталог и группы сообщений;
* тестовые аудиторы и smoke-тесты;
* языковой модуль и его `manifest.json`.

Для каждого языка определи:

| Поле | Требование |
|---|---|
| `code` | ровно нормализованный код, например `ar-sa` |
| `native_name` | название на самом языке |
| `direction` | `rtl` или `ltr` |
| `version` | SemVer, начиная с `1.0.0` |
| `min_crm_version` | минимальная совместимая версия ядра |
| `full_code` | `crm.language-pack-<code>` |
| `type` | строго `language_pack` |
| `category` | `localization` |

Не используйте `ar` в качестве отдельного второго каталога, если продуктовая
локаль — `ar-sa`: ранний слой должен нормализовать краткую форму в основной код.

### 3.2. Источники строк

Строка может находиться в четырёх местах:

1. **Web PHP**: `$t('namespace.key', 'fallback')` и `data-i18n*` в шаблонах.
2. **Web JavaScript**: `window.CRM.i18n.t(...)`, `tr(...)`, `tp(...)`, `mpT(...)`
   и локальные карты, переданные через `json_encode`.
3. **API**: группы в `upload/api/language/<locale>/...` и вызовы `$this->t()` /
   `$lang->get()`.
4. **Модульные строки**: `web/language/<locale>.php` и
   `api/language/<locale>/module/messages.php` внутри пакета.

Нельзя исправлять смешение языков только заменой текста в одном шаблоне. Для
каждого пользовательского текста найдите источник, серверный fallback, клиентский
fallback и путь, по которому строка приходит после AJAX.

### 3.3. Fallback

Fallback обязан быть детерминированным:

* для `ru-ru` базовым fallback является `ru-ru`;
* для остальных локалей базовым fallback является `en-gb`, если регламент проекта
  не определил другой нейтральный язык;
* локаль не должна безусловно объединяться с русским каталогом перед выбором
  пользовательского языка;
* `overrides.php` и `js_overrides.php` должны использовать тот же fallback, что и
  основной каталог;
* отсутствие перевода должно быть видимым результатом аудита, а не незаметным
  возвратом русского текста.

Проверяйте не только наличие ключа: ключ может существовать, но содержать
английскую/русскую заглушку. Для нового языка составьте список разрешённых
языковых символов и отдельно проверьте технические термины, бренды, URL и
плейсхолдеры.

### 3.4. Плейсхолдеры и HTML

Сохраняй без изменений:

* `{name}`, `{count}`, `%s`, `%d`, `%1$s`, `:id` и другие маркеры;
* HTML-теги и атрибуты, если строка действительно возвращает HTML;
* Markdown-ссылки и URL;
* единицы измерения, формат дат и чисел — только по правилам локали.

Не вставляй пользовательские данные в перевод. Если строка содержит HTML,
проверь экранирование и не добавляй `innerHTML` ради простого текста.

## 4. Создание каталога нового языка

### 4.1. Web-файл

Скопируй структуру ключей из актуального `en-gb.php` в новый
`upload/web/language/<locale>.php`. Сохрани вложенные namespace и ключи. Переведи
весь пользовательский текст, включая:

* логин и промо-блок;
* nav, topbar, workspace selector;
* dashboard и все дополнительные виджеты;
* таблицы, фильтры, сортировки, pagination;
* пустые состояния, ошибки, подтверждения, toast и loading;
* модальные окна, формы, placeholder, title и aria-label;
* admin, modules, language management и marketplace;
* темы, настройки, команды, циклы, знания, чаты, уведомления, аналитика,
  тарифы, контрагенты и все остальные страницы.

Новые языки не добавляй секциями в core-файлы `overrides.php`,
`js_overrides.php` или `supplemental/locale_parity.php`: эти файлы содержат
только три базовые локали. Поздние исправления конкретного внешнего языка
помещай в `web/supplemental/packs/<locale>.php` внутри его Marketplace-пакета.
Установщик копирует этот файл в `web/language/supplemental/packs/`, а web и
ранний response-слои подхватывают его после основного каталога. При удалении
пакета supplemental-файл должен удаляться вместе с web/API словарями.

Не копируй русские значения как временную заглушку. Если переводчик пока не
готов, оставь английский нейтральный fallback и зарегистрируй ключ в списке
незавершённых переводов; выпуск пакета с заметными русскими заглушками запрещён.

### 4.2. API-файлы

Создай `upload/api/language/<locale>/manifest.json` и все группы, которые
используются в API. Обычно это:

```text
api/language/<locale>/
├── manifest.json
└── module/messages.php        # если язык поставляется модулем
```

Сверь группы с `upload/api/language/en-gb/` и поиском `$this->t()` /
`$lang->get()`. Ошибка API, сообщение об установке, права, валидация и ответ
пустого результата должны проходить через переводчик. Не переводите MCP-описания
инструментов и машинные JSON-коды.

### 4.3. RTL и LTR

Для `rtl` проверь все слои:

* `<html lang="..." dir="rtl">` устанавливается до отрисовки контента;
* sidebar, topbar, breadcrumbs, dropdown и модальные окна зеркальны;
* иконки направления, стрелки, timeline, таблицы и иерархии не перевёрнуты
  ошибочно;
* числовые поля, даты, коды задач, email, URL и code-block остаются LTR;
* длинные арабские/ивритские строки не обрезаются и не ломают кнопки;
* скролл страницы и горизонтальный скролл таблиц работают на ширине 320–390 px.

Для LTR-языка не переносите RTL CSS. Направление должно следовать manifest и
нормализованной локали, а не содержимому конкретной строки.

## 5. JavaScript и динамический DOM

Это обязательный участок: серверная страница может выглядеть переведённой, но
после AJAX, смены workspace, открытия модального окна или перерисовки виджета
возвращается английский или русский текст.

Для каждого внутреннего маршрута проверьте:

1. В HTML есть `data-i18n`, `data-i18n-placeholder`, `data-i18n-title` и
   `data-i18n-aria-label`, где это необходимо.
2. JS получает выбранный каталог из `window.CRM.messages`, а не из захардкоженной
   русской/английской строки.
3. После `fetch`, pagination, фильтра, смены workspace, drag-and-drop, открытия
   modal и toast вызывается `window.CRM.i18n.applyToDom(root)` для нового DOM.
4. Inline map, если она есть, содержит каждый ключ, переданный в `tr()`.
5. Нет второго элемента-шаблона, который скрыт только CSS, но виден после смены
   состояния и содержит другой язык.
6. `select`, `option`, `aria-live`, `title`, `placeholder`, validation message и
   текст кнопки переведены отдельно.

Проверяйте визуально после клика, а не только по исходному HTML. Особое внимание
обратите на dashboard widgets, kanban, calendar, chat, tasks hierarchy, admin
settings, modules marketplace и workspace switcher.

## 6. Полный аудит внутренних маршрутов

Перед выпуском сформируйте список маршрутов из
`upload/web/config/routes.php`, ссылок шаблонов и навигации. Минимальный набор:

```text
dashboard, ideas, tasks, my-day, my-week, calendar, kanban, gantt,
projects, cycles, analytics, intake, counterparties, teams, knowledge,
notifications, chat, admin, admin-settings, admin-users, admin-statuses,
admin-roles, admin-tags, admin-workflow, admin-webhooks, admin-estimates,
rate-cards, profile, admin-modules, admin-languages, admin-updates
```

Добавьте найденные в текущем коде маршруты, даже если они отсутствуют в списке.
Для каждого маршрута в каждой тестовой локали:

* открыть страницу с чистой сессией/актуальным языком;
* дождаться завершения AJAX и шрифтов;
* пройти страницу от верхней до нижней границы скроллом;
* открыть все доступные вкладки, dropdown, select, modal, tooltip и меню;
* выполнить безопасное действие: фильтр, поиск, переключение представления,
  открытие карточки, смена страницы, смена workspace;
* проверить отсутствие ошибок в console/network;
* проверить desktop и ширину 390 px (дополнительно 320 px для RTL);
* сохранить маршрут, найденную строку, источник ключа, скриншот и шаги
  воспроизведения для каждого дефекта.

Тексты самих пользовательских записей (название задачи, проекта, чата,
workspace) не являются переводом. Их проверяйте отдельно: системные подписи и
кнопки должны быть локализованы, пользовательские данные не изменяются.

## 7. Кэш, сессия и переключение языка

Проверка считается неполной без очистки кэша:

1. Открыть страницу в новом контексте/инкогнито.
2. Установить язык через login selector.
3. Проверить cookie/session и `document.documentElement.lang/dir`.
4. Сделать hard reload без query `lang`.
5. Открыть другой маршрут в той же сессии.
6. Переключить язык туда и обратно без повторного логина.
7. Сменить workspace и проверить, что локаль не сбрасывается.
8. Повторить после выхода и входа.

Нельзя лечить кэш увеличением версии CSS/JS без понимания причины. Проверяйте
HTTP `Cache-Control`, версию ассетов, серверное хранилище локалей и данные
реестра. После установки/обновления пакета новая локаль должна появиться без
ручного удаления пользовательских данных; после удаления пакета нельзя
получить битую cookie или пустой каталог.

## 8. Автоматические проверки до публикации

Запустите из корня репозитория:

```bash
php -l upload/web/language/<locale>.php
php -l upload/web/language/overrides.php
php -l upload/web/language/js_overrides.php
php -l upload/api/language/<locale>/module/messages.php
php upload/api/scripts/audit_web_i18n.php
php upload/api/scripts/audit_api_i18n.php
bash tests/run_local.sh --fast
```

В полном цикле обязательны `bash tests/run_local.sh` и `bash tests/run_all.sh`.
Проверяйте, что аудит действительно включает новый код локали, а не зелёный из-за
пустого/неподключённого каталога. В отчёте должны быть нулевые `failed_count`,
`documentation_drift` и ошибки i18n.

Добавьте тесты, если новый путь или формат их требует:

* ключ присутствует во всех базовых web-каталогах и в новой локали;
* каждая `tr()`-строка есть в inline map;
* API-группы присутствуют и не содержат жёстко заданных пользовательских ответов;
* fallback не отдаёт русский текст в новой локали;
* направление и нормализация `ar`/`ar-sa` (или аналогичной краткой формы)
  стабильны;
* установка, обновление, повторная установка и удаление пакета идемпотентны.

## 9. Формат языкового пакета

ZIP должен быть плоским: `manifest.json` находится в корне архива, а не во
вложенной папке. Рекомендуемая структура:

```text
language-pack-<locale>-<version>.zip
├── manifest.json
├── web/
│   └── <locale>.php
│   └── supplemental/
│       └── packs/
│           └── <locale>.php       # optional late fixes for this pack
└── api/
    └── <locale>/
        └── module/
            └── messages.php
```

Минимальный manifest по образцу арабского пакета:

```json
{
  "type": "language_pack",
  "name": "language-pack-<locale>",
  "full_code": "crm.language-pack-<locale>",
  "vendor": "crm",
  "code": "<locale>",
  "title": "<English title> (<Native name>)",
  "native_name": "<Native name>",
  "direction": "ltr",
  "author": "Anton Barinov",
  "version": "1.0.0",
  "category": "localization",
  "min_crm_version": "<tested core version>",
  "description": "<short localized description>"
}
```

Для RTL поменяйте `direction` на `rtl`. Не добавляйте в ZIP `.env`, дампы,
cookie, временные файлы, `.DS_Store`, исходные секреты, node_modules, тестовые
данные или лишнюю верхнюю директорию. Все PHP-файлы должны пройти
`LanguageFileAstValidator`; запрещённые вызовы и исполняемый код в словарях
недопустимы.

Локальную проверку архива делайте через тот же сервис установщика или UI
администратора. Минимум:

```bash
unzip -l language-pack-<locale>-<version>.zip
sha256sum language-pack-<locale>-<version>.zip
```

Проверьте, что `manifest.code`, пути файлов и имя архива совпадают. Для релиза
сохраните SHA-256 рядом с release-метаданными, но не подменяйте им подпись и не
редактируйте пакет после расчёта hash.

## 10. Установка и обновление на тестовой CRM

Проверьте оба поддерживаемых пути.

### ZIP через админ-панель

1. Войти root-администратором.
2. Открыть **Администрирование → Языки** или **Администрирование → Модули**.
3. Загрузить ZIP.
4. Убедиться, что ошибки manifest, traversal и AST показываются понятно.
5. Убедиться, что локаль появилась в реестре и включена.
6. Сделать hard reload, выбрать язык, пройти маршрутный аудит.

### Установка из marketplace

1. Найти карточку по `full_code`.
2. Проверить title, version, compatibility, direction, description и размер.
3. Установить с включённой проверкой SHA-256.
4. Проверить, что пакет не устанавливается поверх несовместимой директории и
   корректно сообщает `ALREADY_INSTALLED`, `MODULE_DISCOVERED_LOCALLY` или
   `MARKETPLACE_PACKAGE_MISMATCH`.
5. Проверить активность пакета в **Modules** и активность языка в **Languages**.

Для обновления:

* сначала сделать резервную копию и проверить rollback-план;
* увеличить SemVer (patch для исправления перевода, minor для новых ключей,
  major для несовместимого изменения формата);
* сохранить настройки, выбранную локаль, enabled state и пользовательские данные;
* проверить установку поверх предыдущей версии и повторную установку после
  ошибки/обрыва;
* не удалять старые ключи без анализа страниц и совместимости с кэшем;
* после обновления проверить экспорт ZIP и повторный импорт на чистой CRM.

## 11. Публикация в маркетплейсе

Публикация выполняется только с аккаунта владельца и по актуальному регламенту
маркетплейса из CRM Knowledge Base. Агент не публикует секреты и не придумывает
непроверенные endpoint'ы. Если API/панель маркетплейса изменились, сначала
прочитать инфраструктурную страницу Marketplace и зафиксировать фактический
маршрут в рабочей задаче.

Общий порядок:

1. Подготовить пакет и метаданные из раздела 9.
2. Проверить локальную установку, обновление и удаление.
3. Запустить полный локальный тестовый гейт.
4. Зафиксировать commit в `develop` от имени владельца; не добавлять AI в
   author/co-author и не коммитить секреты.
5. Развернуть ту же версию на demo, выполнить браузерный аудит всех маршрутов,
   RTL/LTR и мобильной ширины.
6. В панели/API маркетплейса создать или обновить listing категории
   `localization`/`language_pack` с `full_code`, version, min core version,
   direction, native name, description, changelog, download URL и SHA-256.
7. Убедиться, что каталог отдаёт релиз именно с тем `full_code`, который указан
   в manifest; несовпадение приводит к отказу установки.
8. Проверить download URL по HTTPS, размер, архив без лишней директории и
   повторно проверить checksum после загрузки в marketplace.
9. Опубликовать карточку/релиз только после проверки preview и совместимости.
10. Установить опубликованный релиз на отдельный demo/чистую тестовую CRM через
    marketplace, затем проверить уже установленный production-подобный экземпляр.

В changelog укажите пользовательский результат: добавлены переводы, RTL или
LTR, новые ключи, исправления смешения языков, совместимая версия ядра,
ограничения. Не обещайте полную локализацию, если аудит нашёл непереведённые
видимые строки.

## 12. Браузерный QA-чек-лист

### Общие проверки

* Login: выбран только один язык, весь экран и footer на нём.
* Dashboard: KPI, AI digest, быстрые действия, модальные окна, динамические
  виджеты после reload и AJAX.
* Tasks/hierarchy: дерево, parent/child, фильтры, select, drag-and-drop,
  пустое состояние, мобильный scroll.
* Projects/Kanban/Gantt/Calendar/Cycles: вкладки, даты, статусы, карточки и
  всплывающие сообщения.
* Teams/Counterparties/Knowledge/Chat/Notifications/Analytics: таблицы,
  pagination, редакторы, attachments, search и ошибки API.
* Admin, settings, users, roles, statuses, modules, languages, updates:
  каждый select, tab, confirm, validation и permission state.

### Смешение языков

Для каждого выбранного языка ищите видимые строки на других языках. Допустимы
только бренды, имена пользователей, пользовательские записи, URL, коды и
общепринятые технические обозначения. В отчёт заносите CSS-visible текст, а не
скрытые шаблоны, чтобы отличать реальный дефект от подготовленного DOM.

### RTL/LTR и размеры

Проверяйте desktop, 1024 px, 768 px, 390 px и 320 px. Делайте полный вертикальный
скролл и отдельный горизонтальный скролл таблиц/канбана. Фиксируйте:

* переполнение, наложение, обрезку и невидимые кнопки;
* неверную сторону dropdown/modal/sidebar;
* потерянный focus и неправильный tab order;
* нечитаемые числовые значения и дату;
* console errors, failed network calls и необработанные 4xx/5xx.

## 13. Критерии приёмки

Пакет можно передавать на публикацию только если одновременно выполнены все
условия:

1. Все ключи web/API найдены аудиторами и присутствуют в новой локали.
2. Нет видимого смешения языков на перечисленных маршрутах.
3. Нет безусловного русского fallback для нерусской локали.
4. Серверный HTML и JS после AJAX используют выбранную локаль.
5. RTL/LTR, desktop/mobile и scroll проверены скриншотами.
6. Login, logout, cookie, session, workspace switch и hard reload сохраняют
   ожидаемый язык.
7. ZIP плоский, manifest валиден, AST/SSRF/zip-slip проверки проходят.
8. Установка, повторная установка, обновление, удаление и экспорт работают.
9. SHA-256 загруженного marketplace-релиза совпадает с опубликованным.
10. Полный test gate завершён с `failed_count=0`; документация и changelog
    синхронизированы.
11. Demo проверен после деплоя, а итоговый commit/PR и результат QA записаны в CRM.

## 14. Типовые ошибки и способы диагностики

| Симптом | Причина | Что проверять |
|---|---|---|
| Логин на одном языке, promo на другом | ранний ответ и основной каталог используют разные fallback | `EarlyResponse`, login template, locale cookie |
| После AJAX возвращается английский | отсутствует `js_overrides` или не вызван `applyToDom` | inline map, `data-i18n`, network callback |
| Русский появляется только на dashboard | безусловное слияние `ru-ru` или старый кэш | `I18n::fromRequest`, header, hard reload |
| Ключ есть, но текст английский | в новой локали оставлена английская заглушка | сравнить значения, не только набор ключей |
| API на другом языке | отсутствует группа `api/<locale>` или не нормализован код | `LanguageManager`, `audit_api_i18n.php` |
| RTL ломает стрелки/таблицы | зеркалится направление данных или не применился `dir` | HTML, CSS logical properties, mobile screenshot |
| Marketplace отвечает mismatch | full_code/manifest/package listing различаются | manifest, catalog detail, release hash |
| ZIP не устанавливается | вложенная папка, лишний файл, AST violation | `unzip -l`, `validateArchive()` |
| После обновления старый язык | storage/registry/browser cache не синхронизированы | реестр, enabled codes, cache headers, session |
| Аудит зелёный, UI смешанный | тест проверил наличие ключа, но не видимый DOM | browser scan после кликов и скролла |

## 15. Отчёт агента

Финальный отчёт должен содержать:

* код локали, версию и направление;
* список созданных/изменённых файлов;
* количество ключей web/API, переведённых и оставшихся нейтральными;
* список проверенных маршрутов и размеров viewport;
* результаты `audit_web_i18n`, `audit_api_i18n`, локального и полного гейта;
* результат ZIP install/export и marketplace install;
* SHA-256 опубликованного архива без секретов;
* demo URL/commit/PR и известные ограничения;
* подтверждение, что пользовательские данные, workspace scope, права и сторонние
  модули не изменились.

Документ, runtime-код и задача CRM должны ссылаться на одну и ту же версию
пакета. Любое обнаруженное расхождение после публикации оформляется отдельной
задачей исправления с воспроизводимыми шагами и повторным полным QA.

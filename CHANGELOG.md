# Changelog

All notable public changes to TropaTT should be documented here.

This project follows a lightweight Keep a Changelog style. Dates are added when a release is actually created.

## Unreleased

### Removed

- **The stock installation no longer ships 24 modules — `upload/modules/` now holds nothing but its `.htaccess`.** Every installation used to receive the whole module set (517 files, from `crm.drawio` and `crm.slack-integration` to fourteen migration connectors) whether or not its owner would ever open one of them. All of them are published on the marketplace with signed releases, localised cards and a one-click install from **Administration → Modules → Marketplace**, so the core build no longer has to carry them: a fresh install and every update now deliver the CRM itself and nothing else, and modules are installed on demand. The module system itself is untouched — `modules/vendor.name/` is still the layout, `.htaccess` still denies PHP execution and `manifest.json` inside it, and the discovery/install/activate path is unchanged. The admin dashboard no longer shows the "Шлюз витрин" card when that module is not installed (it used to point at a page that no longer exists). The module code the local test suite exercises (e-commerce gateway, GitHub/GitLab push, WIP limit, the migration connectors) moved to `upload/api/tests/fixtures/modules/`, a git-ignored tree that is neither published nor shipped, and the two module examples the developer guide points at moved to `docs_modules/examples/modules/`, which ships with the documentation instead of the application. `README.md` (three languages), `MODULE_DEVELOPMENT.md` and `docs_modules/modules_*.md` were updated to say where modules come from now.

- **Five module directories left the repository entirely** — `crm.drawio`, `crm.linear-migration`, `crm.notion-migration`, `crm.raycast` and `crm.slack-integration`. Nothing in the core or in the test suite referenced them beyond the marketplace export, and they install from the marketplace like any other module.

### Changed

- **The temp-directory guard of the module installer compares real paths now.** `ModuleRemoteInstaller::extract()` requires the extraction target to sit inside `sys_get_temp_dir()`, but compared a `realpath()`ed destination against the raw setting — on macOS, where `/var` is a symlink to `/private/var`, the guard rejected even the temp directory itself, so `module_marketplace_unit.php` failed locally with "Invalid extraction directory" while passing on Linux. Both sides are now resolved; the check is unchanged in strength.

### Added

- **«Мои персональные показатели» now says whether the period is going well, instead of only how much was done.** The card printed completions, hours, average per task, overdue work, the share stuck for over a week and the logging streak — every one of them a number with nothing to measure it against, so «6 завершённых» was equally consistent with a record month and a collapse. Three blocks answer the question the counter could not. **Goals**: a person's own targets live in the settings the personal preferences already use (`user:<public_id>` scope, name `kpi_goals`) and are read back by the endpoint as `goals` plus `goal_progress_percent` per metric; the card prints the fact next to the target («5 / 8», «50% / 80%», «7ч 10м / 40ч») with the percentage achieved, marking only the goals that were *not* reached, because a met target is not an achievement worth a badge — it is simply not a problem. Validation lives at the reader: a goal of `0`, a blank, a non-numeric value or one outside what the metric can hold (`1…100` for on-time, `1…1000` completions, `1…10080` weekly minutes) means the goal is **off**, never «a goal of zero», so nothing can be divided by it and no card invents progress against a target that does not exist. **Comparison with the scope**: `scope_median_completed`, `scope_median_on_time_percent`, `scope_sample`, `scope_on_time_sample` and the two signed deltas describe the people the actor can actually see (actor + hierarchy descendants + teams they manage, exactly the model the load widget uses), with the median taken over *users* rather than tasks — an idle colleague counts as zero, because that is part of the shape of a team — and a non-root actor whose scope resolves to nobody stays empty instead of silently falling through to the organisation-wide distribution. On-time has no meaning for a colleague without dated work, so those people are left out of that distribution and the sample is reported next to the median; when nobody in scope has a deadline at all, the card says so instead of printing a 0 % verdict, and when there is nobody to compare with it says that too. **Project split**: `completedByProject()` ranks the projects the actor's own period went to, by completions and then by hours, as `projects` (top five) with `projects_total` under it, each row linking into the filtered task list and the head reading «Показаны первые N из M», again under the endpoints' cap rather than pretending the list is complete. The split carries two scopes at once — the actor's own tasks and own work logs, *and* only the projects that actor can reach (`accessibleProjectPublicIds`: created by them, managed by them or on a team of theirs, the same list the stream widgets and the project pickers use) — so it can neither report somebody else's work nor name a project the reader has no access to, and a non-root actor with no accessible project gets an empty list rather than the organisation's project names. Both halves keep the definitions of the tiles above them (completions as `countCompletedTasks`, hours as `sumLoggedMinutes`), with one deliberate exception: work the actor did on a project they cannot reach is still counted by the tiles and is *not* named by the split, so the rows can add up to less than the number directly above them. Not naming the actor's own hour there is the price of never disclosing a project they have no access to, and the audit pins that as intended behaviour instead of leaving it to chance. The card's own «Пока нет данных» state no longer swallows the goal: the early return that stands in for the metric table when the period is completely blank now renders the goals and the comparison under it, because «0 / 8» is exactly the answer somebody opening a fresh period needs, and it is the state the demo admin is in. Being *exactly* at the median is stated as such instead of reading «выше медианы на 0». A goal that was never configured leaves the card pixel-identical to what it showed before. Covered by `analytics_kpi_scorecard_unit.php` (42 assertions: goal-off and goal-zero handling, the divide-by-zero guard, the numeric-string goal, the median over two visible users against a stranger and against a root scope, and the reconciliation of the split with the tiles) and five renderer checks; the seven web locales gained the new labels.

- **«Потоки: загрузка и эффективность» now answers «мы успеваем?», and a portfolio of dozens of streams can be searched and grouped.** The card showed progress, hours, members and a health verdict, but its «Ближайшая веха» column went blank the moment a project had no milestone, and the question a manager actually asks — which stream is late, and by how much — had no column at all. `projectsOverview()` now resolves the nearest **deadline** rather than only a milestone: the milestone when the project has one, otherwise the earliest open task due date, published as `next_deadline_at` / `next_deadline_source` (`milestone` | `task`) — the earliest unresolved deadline in *either* direction, so a stream that missed its date still names it instead of printing a lag over a blank cell — plus `next_future_deadline_at` (the nearest date still ahead, which is what the portfolio line reports), `days_to_deadline`, `schedule_lag_days` (measured from the earliest *missed* deadline, milestone first) and a `schedule_state` of `none` | `ok` | `soon` | `overdue`. The live demo is exactly the case the old column could not describe: all 49 streams carry no dated milestone and no task deadline at all, so every row now says «нет вех/сроков» and the portfolio line states «У 49 потоков нет ни вех, ни дедлайнов задач — отставание по ним посчитать нельзя» instead of leaving 49 blank cells. A project with neither becomes «нет вех/сроков» instead of an empty cell, because "nothing is scheduled" is an answer the reader has to be able to see; a payload that predates the field derives the same verdict from the raw dates rather than inventing a warning. A completed milestone is not a deadline any more (the rule `ProjectSummaryRepository` already used), a soft-deleted or archived task is not one either, and a milestone and a task due on the same day resolve to the milestone — the commitment a client sees. `streamsOverview()` rolls the same scoped rows into `aggregates` — streams in critical/risk/ok, late tasks, late milestones, streams with no schedule at all, the earliest deadline and progress weighted by tasks rather than averaged per stream, so a 3-task project cannot weigh as much as a 300-task one — and the card prints it as a «Портфель» line above the table, with the overdue count linking into the filtered task list and a legend naming how many streams have no dates at all (their lag is unknown, not zero). The table gained client-side search over stream, team and client names — a filter over the payload already in hand, so a keystroke costs no request and can never widen the scope — and grouping by team or client, where the first group holds the most severe stream; long lists cap at ten rows per group. Covered by `analytics_streams_schedule_unit.php` (42 assertions: the milestone/task tie, the deleted and archived exclusions, weighted progress, the honest no-deadline case, the empty non-root scope) and seven renderer checks.

- **The «Активные задачи без учёта времени» block can now be cleared from where it is read.** The block on the «Факт по задачам» card named the tasks whose time was never logged, but the only way to fix one was to open the task and then find its time form. Every listed task now carries a compact «Залогировать время» action that deep-links into the form itself — `index.php?route=task-detail&task_public_id=…&worklog=1` makes the task card activate the «Учёт времени» tab and expand the create form with the minutes field focused, routed through the card's own toggle button so the two paths cannot drift. The marker is ignored when the card does not render that form (external client-portal guests), and the action is styled as a subtle button so it reads as an action beside the task title rather than as part of its link. Covered by a renderer check (`dashboard_insights_widgets.test.js`).

- **`crm_task` can now read checklist items, which the MCP core profile previously could not.** The 27 tools a `core`-profile agent key sees are mega-tools, and the checklist family inside `crm_task` covered `list_checklists`, `create_checklist`, `update_checklist`, `create_checklist_item`, `update_checklist_item`, `delete_checklist` and `delete_checklist_item` — but no way to *read* the items. The fine-grained `crm_list_checklist_items` tool answers that question, and it exists only in the `all` profile, so an agent following its own written workflow (`CRM_WORKFLOW.md` documents `crm_task action=list_checklist_items`) got "Unknown action" and had to drop to REST to see whether a criterion was ticked. The mega-tool now advertises and dispatches `list_checklist_items` to the same handler under `task.manage`, accepting the documented `checklist_public_id` and the `public_id` spelling the mega-tool schema describes, and the permission registry declares the action so it is gated like its neighbours. Covered by `mcp_task_status_alias_unit.php` and the mega-tool contract tests (dispatch arity, schema parity, action permissions).

- **«Факт по задачам» can now point at the work that overran its own estimate.** The estimate block answered «how far off is the plan on average» but never «which task is the problem», which is the only form of that answer a manager can act on. `estimate_overruns` ranks the tasks whose logged minutes beat their own estimate, worst percentage first, each row carrying the task title, the actual and estimated time and the overrun, with the usual «первые N из M» head under `estimate_overruns_total` and a link per row. Only estimates whose unit really is time take part: for a story-point task an overrun would require a points-to-hours conversion the schema does not hold, so a points, t-shirt, complexity or risk estimate is never turned into a fake percentage; currency sets are skipped as everywhere else, a task under its estimate is left out entirely (the block is a to-do list, not noise), and a task carrying two time estimates is counted once, at the larger estimate. Covered by `analytics_estimate_calibration_unit.php` (66 assertions: the exact +100% and +200% cases, the title lookup, and that points-only, soft-deleted, unlogged and under-estimate tasks never appear) and a renderer check.

- **«Факт по задачам» now answers whether the team estimates at all, and how far off it is, instead of only summing hours.** The card showed a total, a median, an average and a coverage percentage — and the average is the one number here that cannot be trusted: a single task carrying a million logged minutes (real data on the demo) pulled the mean to 83 481 minutes against a median of 135. `p90_minutes` and `max_minutes` now sit next to it as «p90» and «Максимум», computed by nearest rank over the whole period rather than over the rendered top ten, with a legend that says what p90 means and how large the sample was. Estimation is reported as what the data actually holds: `estimate_coverage_percent` and `estimated_tasks` answer «do people estimate?», and per estimate set the card prints either the overrun against the estimate (`overrun_percent`, for a set whose unit really is hours) or the cooling rate (`minutes_per_point`, for story points, t-shirt sizes, complexity and the like) — never a points-to-minutes conversion, because `task_estimates` stores points, sizes and severities and there is no mapping to invent. Sets priced in a currency are skipped outright, a set with fewer than `MIN_ESTIMATE_SAMPLE` estimated-and-logged tasks is not reported at all (a rate computed from one task is noise dressed as a measurement), and a task is counted once per set so a duplicated estimate row cannot distort the rate. Under it, `tasks_without_estimate` names the logged tasks nobody estimated, worst first and with titles, capped at five but honest about the total («первые 5 из 23»). The card also gained a project picker (`projects` in the payload, the selected id echoed back as `project_filter`), searchable through the existing `#dashboardInsightActualProjectSelect` binding, narrowing every number, the top list, the activity split and the calibration block to one project. Covered by `analytics_estimate_calibration_unit.php` (55 assertions on percentiles, the per-set rates, the money and one-task exclusions and the filter reach) and five new renderer checks.

- **The working week the dashboard measures load against is now a real, configurable fact instead of a hardcoded 40 hours.** Every load percentage in the analytics widgets divided by the same 2400 minutes, so a company on a 36-hour week read every employee as 11% more loaded than they were, and the cards printed "цель 40 ч" as if that were a property of the organisation. The capacity now resolves in a stated order — an explicit `insights.weekly_capacity_minutes` setting wins, otherwise the best business calendar (the one covering the most weekdays, longest span per day, night shifts handled) is used, otherwise the historical 40-hour default — and the payload says which one applied through `capacity_source`, so the card writes "цель 35ч (по календарю)" instead of guessing. Calendar data is only trusted when it describes a coherent week: fewer than three weekdays is treated as incomplete, and `working_hours` rows whose `business_calendars` parent is gone are ignored outright — exactly the situation on a database that has fifteen such orphaned rows and no calendar at all, where reading them would have produced a nine-hour week. The value is editable in **Administration → Settings** next to the other system settings (scope `system`, name `insights.weekly_capacity_minutes`, 300–6000 minutes validated at the API so a nonsense entry is refused rather than silently ignored) and settable through `PATCH /api/v1/settings/insights.weekly_capacity_minutes`. `my_workload_efficiency` also compares the actor with the people they can actually see: `scope_median_load_percent`, `scope_sample` and `load_vs_scope_median_percent` answer "is my week heavy *for this team*", with the median taken over users (an idle colleague counts as zero) and never over a scope wider than the caller's. Its "Активные (сейчас)" and "Просрочено (сейчас)" tiles became links into the filtered task list. Covered by `analytics_capacity_and_scope_unit.php` (40 assertions on calendar/setting/default precedence, orphaned hours, an incomplete week, the scope median and divide-by-zero — most of them fail on the previous code) and six new renderer checks.

- **Every analytics widget on the dashboard can now be re-cut without reloading the page, and the eight cards answer questions instead of only printing numbers.** Each insights card carries the same segmented toolbar — period (`7`/`30`/`90`, sent to the endpoint) and a client-side sort — remembered per widget in `localStorage`, so reopening the dashboard keeps the view a manager chose. On top of the previous payloads: `my_workload_efficiency` now states whether the queue is winning or losing ("Бэклог растёт: +N за период" / stable / clearing, plus how many days the current backlog takes to clear), separates a live snapshot (active and overdue *now*) from period metrics, shows deadline adherence with its sample size, and prints the weekly target next to the load percentage; `tasks_actual_time` names the active tasks with no logged time (the head says "первые N из M" whenever the endpoint's cap hides the rest) and links straight to the task list instead of only reporting a coverage percentage, and renders activity codes through the localised dictionary; `tasks_completion_velocity` reads the period-scoped cycle-time median, labels the WIP trend (growing/shrinking/stable) and turns the last four weeks plus the open queue into a plainly-worded forecast with a finish date; `workload_efficiency_management` derives a rebalancing recommendation from the overload/underload pair (`Передать N задач: от X к Y`) with links to both people's task lists; `streams_load_efficiency` became a sortable table (risk / overdue / hours / progress) with a next-milestone column and a deep link per row; `stream_detail_load_efficiency` gained a searchable project selector that re-queries the endpoint, a milestones block with overdue highlighting, an estimated time-to-finish at the current pace, clickable members and overdue tasks, and a legend that explains its thresholds. Long lists collapse to ten rows behind "Показать всех (N)". The endpoint grew the fields the new blocks read (`period_daily_minutes`, `created_period`, `backlog_signal`, `backlog_days_to_clear`, `capacity_minutes_week`, `on_time_percent`/`on_time_sample`, `active_without_logs_list`, `cycle_time_median_period_minutes`, `forecast`, `recommendation`, `next_milestone_at`, `milestones`, `throughput_weeks`), cost and bill fields are still stripped, and the API unit test (`analytics_insights_unit.php`, 111 assertions) plus the renderer suite (19 checks, now loading the real module and the shipped `ru-ru` catalog instead of a hand-picked slice of helpers) cover them.

- **The dashboard gained six more analytics widgets, all served by the same insights endpoint.** `GET /api/v1/dashboard/insights` now also answers `my_kpi_scorecard` (personal KPIs — completions, hours, average per task, overdue, share of work stuck for more than a week, consecutive logging days — each with a delta against the previous period), `assignee_department_load` (active and overdue tasks plus weekly hours and load signals per assignee, aggregated per department, where a department is composed from its manager plus their hierarchy descendants and the teams they manage, because `departments` has no member list), `tasks_completion_velocity` (13 weekly throughput buckets, WIP at the end of each week, cycle-time median and 90th percentile and the week-over-week delta), `workload_efficiency_management` (load, efficiency and risk signals with an overload/underload/risk/normal summary), `streams_load_efficiency` (progress, overdue work, hours in the period, member count, next milestone and a health verdict per project) and `stream_detail_load_efficiency` (one project in depth: progress, eight throughput weeks, median cycle time, status split, top five members by hours, next milestones and the overdue list). "Stream" is the owner's term for a project. Visibility is resolved server-side for every widget — personal metrics are self-scoped, people-based widgets use actor + subordinates + managed team members, project widgets use creator/manager/team scope and answer 403 when a requested project is not accessible — an empty non-root scope fails closed, and cost/bill fields are stripped recursively. The catalog, the JS renderers (including the project selector that re-queries the endpoint), the seven web locales, the route docs and the tests grew with them: `analytics_insights_unit.php` now has 67 assertions and the renderer suite 13 checks.

- **Two analytics widgets landed on the dashboard: personal load/efficiency and actual task time.** `GET /api/v1/dashboard/insights?widget=…&period=7|30|90` serves the metric payloads for `my_workload_efficiency` (active and overdue tasks, hours for the last 7 days with a zero-filled daily breakdown, completions and median cycle time inside the period, efficiency = completed / (completed + overdue), load = weekly hours / 40 h with overload/normal/underload signals) and `tasks_actual_time` (top tasks by logged time, median and average per task, coverage of work in flight, and the split by `activity_code`). Cycle time and completion counts come from `task_status_history` because `tasks` has no completion column, terminal statuses are resolved through `TaskStatusSemantics` so a custom dictionary keeps working, and both payloads are scope-checked server-side: personal metrics are self-scoped, task time is limited to the actor's visible users, an empty non-root scope fails closed, and cost/bill fields are stripped recursively before the response leaves the service. The new `InsightsController` plus the `InsightsRepository` aggregates are covered by `analytics_insights_unit.php` (30 assertions: overdue/terminal handling, zero-filled week, first-transition cycle time, median/average, activity order, root vs scoped vs empty scope).

- **Modules can finally schedule their own cron work.** `ModuleServiceProviderInterface::getScheduledTasks()` was documented as the way a module registers background tasks (`ModuleCronScheduler::registerTask()` even has a dedicated docblock for it), but nothing ever consumed the declaration: `ServiceProviderRegistry::getAllScheduledTasks()` had no caller anywhere in the codebase, so `module_scheduled_tasks` stayed empty on real installations and every module cron path was dead — most visibly the e-commerce gateway's transactional outbox, whose `order.status_changed` events (E-COM-04) piled up in `pending` and never reached a storefront. `ServiceProviderRegistry::getScheduledTasksByModule()` now keeps the owning module name that `registerTask()` keys its rows by, and `App::initModuleSystem()` registers every declared task on each request through the idempotent `ModuleCronScheduler` (one row per `module_name` + `task_name`, schedule changes recomputed, duplicates collapsed). Covered by `module_cron_task_registration_unit.php`.

- **The connector line now covers OpenCart / ocStore 2.3.x, the version most stores in RU and the CIS actually run.** `connectors/opencart-2.3/` ships admin and catalog extensions in the 2.3 layout (`.tpl` PHP templates rather than Twig, controllers under `extension/`, the extensions list at `extension/extension&type=module`, the `token` session instead of `user_token`, languages for `ru-ru` and `en-gb`), registers its order hook through `model('extension/event')->addEvent('tropatt_order_history', 'catalog/model/checkout/order/addOrderHistory/after', 'extension/module/tropatt/onOrderHistoryAdd')` — 2.3 has the `event` table but `deleteEvent()`, not `deleteEventByCode()` — and answers the CRM webhook with the same outbound signature scheme as the other connectors (`base64(HMAC-SHA256(secret, timestamp . '.' . raw_body))`, ±300 s, constant-time compare) plus the four-argument `addOrderHistory()` of 2.3. Because the event fires around *every* model method call in 2.3, no core file is touched; `install.xml` is a documented OCMOD fallback for builds where the mechanism is switched off, and the README states plainly that enabling both mechanisms doubles every request. The payload is not a copy of the 3.0 connector's: legal requisites are recognised in custom fields (INN → `billing_entity.tax_id`, KPP, legal name, legal address, bank details — including the shapes SimpleCheckout 4.x/4.9.x writes), `shipping_iso_code_2` provides the ISO country code instead of the country name, the order comment travels in the contract field `comment`, amounts are scaled by the store currency's `decimal_place` with `currency_minor_unit` (zero-decimal currencies used to be off by 100), a negative OpenCart coupon total becomes a positive `discount_total` (the validator rejects a negative `amount_minor`, so such an order used to be refused outright), a fractional quantity is rounded to a whole number with the original kept in the line options, and `paid` follows a configured list of paid order statuses instead of a hard-coded `false`. The connector also carries the batch stock endpoint the task specified — `route=extension/module/tropatt/syncStock`, signed like the webhook, `mode=pull` returning a paginated catalogue snapshot whose count and page are read inside one transaction, `mode=push` applying a batch inside one transaction with `SELECT ... FOR UPDATE` on every row it rewrites and a `dry_run` mode that rolls back. Distributed as `connectors/dist/tropatt-opencart-2.3.ocmod.zip` (built from `upload/`, `install.xml`, `README.md`, `LICENSE`; the README documents the `zip` command). The connector contract test grew a section that *executes* the 2.3 code against a minimal OpenCart harness and validates the payload it produces with the real `PayloadValidator`/`SignatureService` — 65/65 checks — and that test is now part of the local pre-flight (`tests/run_local.sh`, module step), where it previously was not run by anything. Honest gaps: the CRM has no stock ingestion endpoint yet, so `syncStock` has no counterpart inside the gateway (recorded as a follow-up task) and only `mode=pull`/`mode=push` behaviour on the store side is verified; the task also asked for a separate public repository (`tropatt-opencart-2.3`), and like the 3.0 and 4.0 connectors this one lives in the monorepo — publishing it is an owner decision.

### Fixed

- **Deleting an already archived project (or an already deleted task) answered 404, so nothing could ever confirm a fixture was gone — the release gate leaked one project and one task on every run.** `ProjectService::delete()` archives: `ProjectRepository::archiveByPublicId()` carries `whereNull('archived_at')`, so on a repeated DELETE the row was found but the statement updated nothing and the call surfaced as `PROJECT_NOT_FOUND`; `TaskService::delete()` answered `TASK_NOT_FOUND` for an already soft-deleted row the same way. DELETE is now idempotent — both services check access/manage rights *first* (an unreadable row still confirms nothing) and then count an already archived or deleted row as deleted. The sweep that keeps the demo clean was blind for the same reason and is fixed with it: cleanup archives the project before deleting its tasks, and after that the tasks of an archived project are absent from the default list views (`projects` filters `archived_at IS NULL`, the task list hides rows whose project is archived), so a sweep that asked for the defaults could never see — let alone remove — what a previous run had archived, and the fixtures accumulated monotonically (35 projects and 24 tasks on the demo). `tests/mcp_e2e/insights_scope_check.py` now asks both views for the archive (`archived=1`, `include_archived_projects=1`), and the audit grew three checks around it: re-deleting an archived project is idempotent, a task of an archived project stays reachable for the sweep, and a second sweep pass after cleanup must be a no-op — the last one used to report `{projects: 1, tasks: 1}` on every single run without failing anything. Verified live on the demo before and after: the same project answered `HTTP 200` then `HTTP 404` and now answers `HTTP 200` twice, with the leaking task visible to the sweep only through the archive flag.

- **Creating a task in a project with no task-key prefix answered "Внутренняя ошибка сервера" instead of creating the task.** `TaskKeyService::assignNextTaskKey()` fell back to the literal `'PRJ'` whenever `projects.task_key_prefix` was `NULL`, and because the counter is kept **per project**, the *second* prefix-less project started again at `PRJ-1` — a key already taken by the first, so the row hit the unique index `uq_tasks_task_key` and the insert surfaced as a bare 500 (`"Controller invocation failed"` in the log). The migration that backfills NULL prefixes could not prevent it: a project can become prefix-less *after* it ran, and any such project 500'd on its first task. A project without a stored prefix now derives one from its own title, makes it unique against every other project, and **stores it on the project**, so the counter, the key and every later card in that project agree on one prefix; the fallback is gone, which means a project can no longer silently key its tasks under another project's namespace. The first-task collision is also handled where it can only be detected — at the insert — by retrying with the next key (narrowly matched to the `task_key` index, so a `public_id` or row-version clash is never retried as if it were a key clash), because an exhausted counter is not a server error. `ProjectTaskKeyPrefixBackfillMigration` repairs existing rows and is registered in `MigrationManager`, the counter repository lost its MySQL-only `INSERT IGNORE` / `FOR UPDATE` dependence, and `generateProjectPrefix()` no longer lets a three-digit suffix overflow the `VARCHAR(10)` the column holds. Covered by `project_task_key_prefix_unit.php` (25 assertions: the derived and de-duplicated prefix, the concurrent-writer adoption, the retry sequence, the migration) — verified live on the demo before and after: the same project that answered **HTTP 500** answers **HTTP 201** with `QATESTPREF-2`, a second prefix-less project with the same title gets a distinct `QATESTPRE2`, and a deliberately forced key collision is answered with the next key instead of a 500.

- **The weekly series behind the KPI card dropped everything logged *today* on any server east of UTC — the demo's own timezone included.** `InsightsRepository::dailyMinutes()` builds the zero-filled day list from the window's two ends and labels it with `gmdate()`, but parsed both ends as *local* midnight: on a UTC+3 host the range came out as `[from − 1 day, to − 1 day]`, so the last day of the window was never emitted. The SQL still grouped today's minutes correctly — the day they landed under was simply never printed, which is why the live demo answered `minutes: 120` for somebody who had just logged two hours and `weekly_minutes_last: 0` in the very same payload, and why that card's newest bar was always empty there. The cost was not cosmetic: the weekly KPI goal this release adds (`goal_progress_percent.weekly_minutes`) read 0 % against an afternoon of work, and the same series feeds the card's trend percentage. The day list is now built in UTC, like the timestamps it buckets, and the week arithmetic moved with it — `weekKeyFor()` parses its day as UTC, and the new `mondayTsUtc()` derives the bucket base from `gmdate('N')` instead of `strtotime('monday this week')`, which resolves in the server's timezone and labelled every `week_start` a day early on exactly those hosts (a Sunday for a Monday-start week; the velocity card's buckets share that code path). - **A failed update can be rolled back again instead of stranding the installation in maintenance mode.** On the demo stand an update job died while writing files (`copy(...): Permission denied`), which left the job state at `failed` with the *apply* progress still stored; the first rollback attempt then failed on its own token check and wrote `state = rollback_failed` while the progress still belonged to the apply phase. On work.tropatt.com 57 tasks had accumulated in `new` before this change, and the task list had to be normalised by hand. `TaskRepository::defaultStatusCode()` now resolves the first active, non-terminal `task` status by `sort_order` (ignoring closed and inactive entries, tolerating `NULL is_closed`), and the service falls back to `new` only when the dictionary is empty or unavailable — so installations seeded with `new` keep their behaviour, and installations with their own dictionary get a valid default. - **Transient TLS/network failures no longer fail the release gate.** A client-side VPN or proxy stall, or an idle keep-alive connection the web server already closed, surfaces as `SSL: UNEXPECTED_EOF_WHILE_READING` — the connection dies before any HTTP response exists, so a few calls in a row fail and the rest of the run succeeds. The suite's HTTP client (`tests/lib/http_client.py`) retried once after one second, which a ~10-second stall defeats, and the gate was red for a problem that was never in the CRM: on 2026-09-14 the demo served 250 MCP requests in the failing minute (125×`200`, 115×`429`, no `5xx`) while the failing calls never reached the web server at all. Transport failures are now classified (`SSLEOFError`, connection reset/abort, remote-disconnected, incomplete read, timeouts) and retried with exponential backoff (0.5 s → 2 s → 5 s), each retry on a freshly built TLS context so a rejected session ticket cannot poison it; a non-transient error still fails immediately, and `retries=0` still reports the raw failure. `tests/checks/http_client_resilience.py` exercises this offline against a server that drops connections (8 checks) and is wired into the gate as its own step, so `failed_count` covers it.
- **A MySQL deadlock in the rate limiter no longer silently skips the counter.** `DatabaseRateLimiter::fetchForUpdate()` caught a deadlock (`SQLSTATE[40001]`, 1213) or lock-wait timeout (1205), wrote it to `error_log()` — which stock PHP-FPM discards — and returned `null`, so `hit()` believed the row was missing: it then called `commit()` on a transaction InnoDB had already rolled back and never incremented the counter. Under the parallel bursts that cause deadlocks in the first place (the access log shows them on nearly every MCP run) the limiter therefore stopped counting exactly when the load was highest. The statement is now retried once inside a fresh transaction (the caller's `commit()` stays valid), a second failure is logged through `AppLog` and propagated to the existing fail-open handler instead of being disguised as "no row", and all eleven `error_log()` calls in the class were routed through `AppLog`.

Covered by `module_migration_runner_unit.php`, which now re-installs over a leftover schema (including the two-clause `ALTER` shape) and asserts that a broken migration still fails.

A module that is registered but not enabled — the real state of the module in the report — now offers the step that was actually left: "Активировать", with confirmation, in all 7 locales. Covered by `admin_modules_marketplace.test.js` (17 tests: it drives the shipped `mpCardState()` with pending/errored/ready lists and asserts the grid passes the readiness and re-renders), now wired into the local pre-flight as `npm run test:admin-modules`. - **The update server can no longer lose its build registry to a failed write, and can rebuild it if it does.** On 2026-09-14 the update center's `storage/cache/core_builds.json` and `update_channel_history.json` were left at 0 bytes (a write that failed with `errno=28 No space left on device`, plus an unguarded `json_encode()` result), so `build-status` was empty, every channel lost `latest_build_id`, `update-plan` returned no target — and **no installation could update any more, old or new** — while the 10-minute cron kept logging `SUCCESS`. Each MySQL connection now raises `wait_timeout` on its own session (600 seconds by default, `wait_timeout` under the connection config overrides it, best-effort when a host refuses), recovery rebinds the cached `db.pdo` so services resolved after it use the live handle, `Container::forget()` lets a caller evict an instance built on the closed handle, and `IdeaService` resolves its handle per query instead of capturing it once — so a service created before the AI call keeps working after a reconnect.

The provider-health write then threw a `PDOException` straight out of `AiProviderService::completeText()`, and `AiActionService::execute()` reported it as `AI_PROVIDER_UNAVAILABLE` — the successful answer was thrown away and the job was marked failed. Provider health is diagnostic telemetry and is now written best-effort (a failure is logged as `ai_provider_health_write_failed`), the same is true of the job/usage bookkeeping (`safeBookkeeping`), and a lost connection is logged as such instead of being blamed on the provider. In addition, `ConnectionManager::reconnect()` opens a genuinely new handle — the previous "reconnect" re-read the cached one, so `db.pdo` handed back the very connection that had just failed; the idea AI steps now use the new `db.reconnect` binding and log a recovered connection as a warning rather than an error.

A unit test pins the contract tool by tool so a new AI action cannot be added without the guard.
